# Kleo Document Chat

A document-grounded chat application built for the Kleo Full-Stack Developer take-home.

Users can create persistent conversations, upload PDF, TXT, or Markdown files, and ask questions about those sources. Responses are streamed and grounded in retrieved document chunks. When an answer uses document evidence, the UI shows the source filename, page or section when available, and the relevant excerpt.

## Links

- Live demo: https://kleo-document-chat-coral.vercel.app
- GitHub: https://github.com/florinalabs/kleo-document-chat

## Features

- Persistent chat conversations stored in Neon
- PDF, TXT, Markdown, and `.markdown` uploads
- Page-aware PDF text extraction
- Overlapping text chunks for retrieval
- 768-dimensional Gemini embeddings stored with pgvector
- Chat-scoped semantic search
- Streamed responses with the Vercel AI SDK
- Inline source references such as `[S1]`
- Expandable evidence cards with verified source metadata
- Dedicated Sources tab for each conversation
- Source and chat deletion
- Loading, empty, success, and error states
- Chat history that survives reloads

## Architecture

Document ingestion:

```text
Upload file
   ↓
Extract text
   ↓
Split into chunks
   ↓
Generate embeddings
   ↓
Store document, chunks, and vectors in Neon
```

Question answering:

```text
User question
   ↓
Generate query embedding
   ↓
Search relevant chunks with pgvector
   ↓
Restrict results to the active chat
   ↓
Create server-owned source IDs (S1, S2, ...)
   ↓
Send evidence and conversation history to Gemini
   ↓
Stream the grounded answer
   ↓
Resolve showEvidence output on the server
   ↓
Render evidence cards
   ↓
Persist the completed conversation
```

The model only refers to source IDs such as `S1`. The filename, page number, section, and excerpt shown to the user come from the server-side retrieval result rather than being generated by the model.

## Database schema

The application uses four tables:

```text
chats
├── messages
└── documents
     └── document_chunks
          └── embedding vector(768)
```

The checked-in schema is in `db/chat-schema.sql`.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE IF NOT EXISTS chats (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  chat_id UUID NOT NULL
    REFERENCES chats(id)
    ON DELETE CASCADE,

  role TEXT NOT NULL
    CHECK (role IN ('user', 'assistant')),

  parts JSONB NOT NULL,
  position INTEGER NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (chat_id, position)
);

CREATE TABLE IF NOT EXISTS documents (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  chat_id UUID NOT NULL
    REFERENCES chats(id)
    ON DELETE CASCADE,

  filename TEXT NOT NULL,
  mime_type TEXT NOT NULL,
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS document_chunks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

  document_id UUID NOT NULL
    REFERENCES documents(id)
    ON DELETE CASCADE,

  content TEXT NOT NULL,
  chunk_index INTEGER NOT NULL,
  page_number INTEGER,
  section TEXT,
  embedding VECTOR(768),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (document_id, chunk_index)
);

CREATE INDEX IF NOT EXISTS idx_documents_chat_id
  ON documents (chat_id);
```

The foreign keys use `ON DELETE CASCADE`, so deleting a chat removes its messages, documents, chunks, and embeddings. Deleting one document removes its chunks.

### Chat isolation

Retrieval is scoped to the current conversation:

```sql
FROM document_chunks dc
JOIN documents d
  ON d.id = dc.document_id
WHERE d.chat_id = $CURRENT_CHAT_ID
```

This prevents a document uploaded in one chat from being retrieved in another.

## Retrieval and citations

Stored chunks are embedded using the `RETRIEVAL_DOCUMENT` task type. User questions use `RETRIEVAL_QUERY`. Both use 768 dimensions.

Retrieval uses pgvector cosine distance with the `<=>` operator. The chat route retrieves candidate chunks, removes duplicates, and sends at most five evidence sources to the model.

For example:

```text
S1 → contract.pdf, page 2
S2 → policy.md
```

Gemini can write `[S1]` in its answer and call `showEvidence` with `S1`, but the server resolves that source ID back to the actual retrieved chunk before returning the filename, location, and excerpt shown in the UI.

If the evidence is not enough to answer the question, the assistant is instructed to return:

```text
I couldn't find that in the uploaded document.
```

## Structured evidence UI

The chat route exposes a `showEvidence` tool through the Vercel AI SDK.

The model supplies only source IDs:

```json
{
  "sourceIds": ["S1", "S2"]
}
```

The input is validated with Zod. The server resolves those IDs against the evidence retrieved for that request, then the client renders the result as expandable evidence cards.

I chose evidence cards because they let the user verify a document-grounded answer without leaving the conversation.

## Document ingestion

Supported formats:

- PDF
- TXT
- Markdown (`.md` and `.markdown`)

Current limits:

- 4 MB maximum file size
- 50-page maximum for PDFs
- unsupported file types are rejected
- empty documents are rejected

PDFs are processed page by page before chunking. This prevents chunks from crossing page boundaries and lets citations retain a page number.

The current chunker uses roughly 1,000 characters per chunk with 150 characters of overlap.

## Decisions and trade-offs

### Simple chunking

I used character-based chunking with overlap to keep ingestion predictable within the timebox. For a larger system I would compare it with token-aware or semantic chunking.

### Retrieval without reranking

The current implementation uses cosine vector search and deduplication. With more time I would test similarity thresholds, hybrid keyword/vector retrieval, and reranking.

### No approximate vector index

The data set for this take-home is small and retrieval is already scoped to one chat, so exact cosine search is sufficient. At larger scale I would benchmark an HNSW index using `vector_cosine_ops`.

### Markdown metadata

PDF page numbers are preserved. TXT and Markdown currently fall back to filename and excerpt rather than extracting Markdown heading metadata.

### Sequential ingestion

Chunk writes are currently sequential. A production version would batch inserts and use a transaction so a failed ingestion cannot leave partial data.

### Source deletion

Deleting a source removes it and its chunks from future retrieval. Evidence already persisted inside an older assistant message can remain visible in historical chat output until that chat is deleted. In a privacy-sensitive production system I would redact those historical tool outputs or store evidence references separately.

## AI tools used

I used ChatGPT for implementation support, debugging, code review, test planning, and README review.

Generated suggestions were tested against the installed libraries and the running application rather than accepted automatically.

### Example where I corrected AI-generated output

While implementing the evidence tool, one suggestion added another model step after `showEvidence`. Testing showed that it caused the textual answer to be generated twice, so I removed the extra step and kept one generation where Gemini writes the answer and calls `showEvidence` in the same response.

Another suggestion called `destroy()` on the PDF proxy returned by the installed `unpdf` version. The TypeScript definitions for the version used by this project did not expose that method, so I removed the call after checking the actual API.
